# Как работать с этим репозиторием

Файл читает каждая новая сессия. Он существует, чтобы заказчику не приходилось
пересказывать правила и состояние заново: память проекта лежит в репозитории, а
не в переписке.

## Что прочитать первым делом

Порядок не случайный: каждый следующий файл понятен только после предыдущего.

1. **Этот файл** — правила и порядок работы.
2. **`README.md`** — что за продукт, как он устроен и как его развернуть.
3. **`docs/spec.md`** — продуктовый контракт и критерии приёмки. Там
   зафиксированы решения, включая те, что выглядят странно, но приняты
   осознанно.
4. **`docs/грабли.md`** — на чём этот проект уже наступал в бою. Короткий файл,
   который экономит день отладки.
5. **`docs/handoff/`** — по нужной теме: там причины, а не только результат.

## Как работать с заказчиком

- **Один pull request на сессию.** Вся работа сессии идёт в одну ветку
  `claude/telegram-max-bot-mvp-edbbfq` и в один PR. Не открывать второй PR на ту
  же ветку и не открывать PR на каждую задачу внутри сессии: коммиты
  докладываются в уже открытый.
- **Мержит заказчик сама.** Не мержить PR, не включать авто-мерж, не пушить в
  `main`. Работа сессии считается сданной, когда она запушена в ветку и PR
  открыт, — дальше её ход.
- **Выкладка только по явному слову заказчика.** Она выкатывает сама, через
  Railway. Само по себе «готово» — не разрешение выкладывать.
- **Задачи приходят маленькими поручениями.** Сделать ровно поручённое.
  Заметил постороннюю проблему — сказать словами, а не починить заодно.
- **Готовый код отдавать целым файлом, а не диффом.** Заказчик правит файлы
  через веб-интерфейс GitHub, и патч там применить нечем.
- **Никаких заглушек и имитаций.** Если работу нельзя сделать честно —
  остановиться и спросить, а не подставить правдоподобную пустышку.
- **Беречь токены.** Не перечитывать целые файлы, когда нужен один участок; не
  гонять весь прогон дважды подряд; не опрашивать лог в цикле, пока смоук идёт.

## Постоянные правила заказчика

Они не обсуждаются и действуют всегда:

- **Секреты только через переменные окружения.** `.env` в `.gitignore`, в
  репозитории — `.env.example`.
- **Комментарии, документация и тексты для человека — по-русски.** Код, имена,
  сообщения коммитов — по-английски.
- **Вебхуки проверяются по секрету.** Telegram — `secret_token`, MAX — его
  аналог из документации.
- **Входящее фото ограничено по размеру, MIME-тип проверяется до отправки
  провайдеру.**
- **В логах нет содержимого сообщений и токенов.** Идентификатор пользователя —
  можно.

## Ключевой инвариант

**Лимит не списывается за упавший запрос.** Списание — только по факту
успешно доставленного человеку результата. Отсюда форма всех сценариев:
проверили остаток → сделали работу → доставили → списали.

Исключение ровно одно и оно осознанное: учёт обращений к провайдеру
(`generations`) пишется сразу после ответа провайдера, не дожидаясь доставки.
Лимит — про справедливость к человеку, учёт — про уже потраченные деньги.

## Где что лежит

```
app/core/       сценарии, лимиты, тарифы, тексты. Чистый Python, ноль I/O
app/ports/      протоколы: хранилище, мессенджер, провайдеры, оплата
app/adapters/   telegram/, max/, storage/, ai/, payments/
app/infra/      очередь, повторы, предохранитель, ограничитель, логи
config/         реестр пресетов и системный промпт — точки расширения
assets/presets/ примеры к приколам: на каждый прикол нужен <id>.jpg
docs/spec.md    продуктовый контракт и критерии приёмки
docs/грабли.md  на чём уже наступали
docs/handoff/   что сделано в каждой фазе и почему именно так
docs/legal/     оферта и политика; там же незаполненные плейсхолдеры
```

Продуктовая логика написана один раз и живёт в `app/core/`. Мессенджеры
отличаются только адаптерами: если ради MAX понадобилось трогать `core/` —
что-то спроектировано неверно.

## Прежде чем писать код

1. **Прочитать `docs/spec.md`** по нужному разделу.
2. **Посмотреть `docs/handoff/`** по теме — там причины, а не только результат.
3. **Заглянуть в `docs/грабли.md`**, если работа касается MAX, картинок,
   оплаты, очереди или тестов по базе.
4. Комментарий объясняет **почему**, а не что. «Что» видно из кода.

## Проверки перед пушем

```bash
ruff check . && ruff format --check . && mypy && pytest -q
python scripts/check_texts.py     # правила §2.9 для всех экранов
```

Те же команды выполняет CI на каждый пуш.

Контрактные тесты хранилища идут против настоящего PostgreSQL:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://bot:bot@127.0.0.1:55432/botdb pytest -q
```

Без этой переменной они пропускаются — и половина гарантий вместе с ними.

Новый тест проверяется мутацией: сломать поведение, убедиться, что тест
упал. Тест, который не падает ни на одной поломке, не охраняет ничего.

## Чего делать нельзя

- Писать строки интерфейса где угодно, кроме `app/core/texts.py`. Строка в
  обработчике — блокирующая ошибка на ревью.
- Класть в логи и в базу содержимое сообщений, описания картинок и токены.
  Идентификатор пользователя — можно.
- Менять `id` выпущенного пресета: он лежит в данных кнопок, а кнопки живут в
  переписках вечно.
- Делать пресет «просто ещё одним обработчиком». Новый пресет — это запись в
  `config/presets.py` и больше ничего (критерий приёмки A1).
- Мержить свой PR, пушить в `main` и выкладывать на Railway без слова
  заказчика.
