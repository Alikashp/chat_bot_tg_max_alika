# Чат-бот для Telegram и MAX

Бот с чатом, картинками по описанию и обработкой фото. Работает в двух
мессенджерах: Telegram и MAX.

**Текущее состояние: фаза 2 из 9 — инфраструктура надёжности.** Бот отвечает
«понг» на любое сообщение; под этим уже лежат ограниченная очередь с
backpressure, пул воркеров, дедупликация повторных доставок, ограничитель
частоты, повторы с разбросом задержки и предохранитель на провайдера.
Продуктовые сценарии приходят начиная с фазы 4; порядок работ и что уже
сделано — в [docs/plan.md](docs/plan.md).

## Как развернуть с нуля

### 1. Завести ботов

**Telegram.** Написать [@BotFather](https://t.me/BotFather), команда `/newbot`,
получить токен вида `123456789:AA...`.

**MAX.** Найти в мессенджере `@MasterBot`, команда `/create`, получить токен.
Понадобится начиная с фазы 7. Учтите: с августа 2025 публиковать ботов в MAX
могут только верифицированные российские юрлица.

### 2. Придумать секрет вебхука

```bash
python -c "import secrets; print(secrets.token_hex(24))"
```

Один секрет годится обоим мессенджерам: алфавит MAX (`A-Z a-z 0-9 -`) строго
уже телеграмного, и `token_hex` в него укладывается.

### 3. Запустить локально

Нужен Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env
# заполнить TELEGRAM_BOT_TOKEN, TELEGRAM_WEBHOOK_SECRET, PUBLIC_URL
```

Проверить, что всё цело:

```bash
ruff check . && ruff format --check . && mypy && pytest -q
```

Запустить:

```bash
python -m app.main
```

При старте приложение само зарегистрирует вебхук по адресу из `PUBLIC_URL`.
Локально это значит, что нужен HTTPS-туннель наружу (например `cloudflared`
или `ngrok`), а его адрес — в `PUBLIC_URL`. Оба мессенджера принимают вебхуки
только по HTTPS с сертификатом доверенного центра; MAX вдобавок требует, чтобы
внешний порт был одним из `80`, `8080`, `443`, `8443`, `16384`–`32383`.

### 4. Выкатить на Railway

1. Создать проект и подключить этот репозиторий. Пуш в `main` → автодеплой.
2. Прописать переменные окружения из таблицы ниже. `PORT` Railway подставляет
   сам, задавать вручную не надо.
3. `PUBLIC_URL` — публичный домен сервиса из вкладки Settings → Networking,
   вместе с `https://`.
4. Healthcheck-путь `/health` уже прописан в `railway.json`, отдельно
   настраивать не требуется.

Сервис — один процесс, слушает `$PORT`, пишет логи в stdout в формате JSON.
При выкатке Railway шлёт `SIGTERM`; приложение перестаёт принимать обновления,
даёт текущим задачам доработать и только потом завершается.

## Переменные окружения

| Имя | Обязательна | Назначение | Где взять |
|---|---|---|---|
| `TELEGRAM_BOT_TOKEN` | да | Токен бота Telegram | [@BotFather](https://t.me/BotFather), `/newbot` |
| `TELEGRAM_WEBHOOK_SECRET` | да | Подпись запросов вебхука. Минимум 16 символов, только `A-Z a-z 0-9 -` | `python -c "import secrets; print(secrets.token_hex(24))"` |
| `PUBLIC_URL` | да | Публичный адрес сервиса, только `https://`. Из него собирается адрес вебхука | Railway → Settings → Networking |
| `PORT` | нет (8080) | Порт HTTP-сервера | Railway подставляет автоматически |
| `APP_ENV` | нет (`production`) | `local` включает читаемые логи вместо JSON | — |
| `LOG_LEVEL` | нет (`INFO`) | `DEBUG`, `INFO`, `WARNING` или `ERROR` | — |
| `SHUTDOWN_TIMEOUT_SECONDS` | нет (20) | Сколько секунд дать задачам доработать после `SIGTERM`. Должно быть меньше `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` | — |
| `QUEUE_CAPACITY` | нет (1000) | Сколько обновлений помещается в очередь; за пределом мессенджер получает отказ и повторит доставку | — |
| `QUEUE_WORKERS` | нет (16) | Сколько обновлений обрабатывается одновременно | — |
| `DEDUP_TTL_SECONDS` | нет (600) | Сколько помним ключ обновления, чтобы не обработать повтор дважды | — |
| `DEDUP_MAX_KEYS` | нет (100000) | Потолок числа запомненных ключей — защита от роста памяти | — |

Таблица пополняется вместе с фазами: переменные провайдеров ИИ появятся на
фазе 5, базы данных — на фазе 3, оплаты — на фазе 8.

## Устройство

Продуктовая логика не знает ни про Telegram, ни про MAX, ни про конкретного
провайдера ИИ. Сценарий пишется один раз и работает в обоих мессенджерах;
различаются только формат клавиатур и вызовы отправки.

```
app/
  core/       сценарии, лимиты, тарифы, тексты. Чистый Python, ноль I/O
  ports/      протоколы: Storage, LLMProvider, ImageProvider,
              PaymentProvider, Messenger
  adapters/   telegram/, max/, storage/, ai/, payments/
  infra/      очередь и воркеры, дедупликация, ограничитель частоты,
              повторы и предохранитель, HTTP-сервер, логирование
config/       реестр пресетов обработки фото
scripts/      нагрузочная проверка, линтер текстов
tests/
  contract/   тесты портов, общие для всех реализаций
  unit/       модульные тесты
  integration/ сквозные проверки
```

Путь обновления: вебхук проверяет секрет, отбрасывает повтор по ключу
обновления, кладёт задачу в очередь фиксированной ёмкости и отвечает. Работу
делают воркеры вне HTTP-запроса. Если очередь полна, приходит `503`, и
мессенджер повторит доставку позже — сообщение пользователя не теряется.

Запрет на I/O в `core/` и `ports/` не на словах: его проверяет
`tests/unit/test_core_is_pure.py`, который валится на любом импорте aiogram,
maxapi, httpx, aiohttp или драйвера БД.

Все тексты интерфейса живут в `app/core/texts.py`. Строка в обработчике —
блокирующая ошибка на ревью.

## Проверки

```bash
ruff check .          # линтер
ruff format --check . # форматирование
mypy                  # типы, strict на core/ и ports/
pytest -q             # тесты
```

Те же четыре команды выполняет CI на каждый пуш.

Нагрузочная проверка (критерий приёмки №12) запускается отдельно, по живому
сервису:

```bash
python scripts/loadtest.py \
    --url https://ваш-сервис.up.railway.app \
    --secret "$TELEGRAM_WEBHOOK_SECRET" \
    --rps 30 --duration 60
```

Скрипт печатает коды ответов, задержки, глубину очереди и возвращает ненулевой
код, если проверка не пройдена.
