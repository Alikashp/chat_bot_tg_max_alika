Дата: 2026-10-03. Ветка `claude/telegram-max-bot-mvp-edbbfq`.

Поручение сессии 7: три шага, критерии В1–В6 — в `docs/plan.md`, раздел

коммит, тест писался раньше кода, новые тесты проверены мутацией (все
мутации убиты), тесты по базе прогнаны против PostgreSQL. Вопросов

## Что изменилось

| Шаг | Что было | Что стало |
|---|---|---|
| 1 | Текст «Готово! Файлы выше» с кнопками приходил раньше файлов; под ним — кнопки всех действий раздела | «Готовлю…» становится «Вот файлы 👇», под ним файлы, потом текст и ровно две кнопки (без ключа презентаций — одна) |
| 2 | Тема → выбор оформления → сборка | Тема → экран параметров, заполненный по умолчанию → «Собрать». Через экран идут все пути |
| 3 | Презентация только по теме или докладу | Ещё и по файлу: pdf, docx, pptx, txt до 20 МБ — вместо темы или кнопкой «📎 Материал» |

## Шаг 1. Результат доклада

`app/core/scenarios/documents.py`: файлы → списание → «Вот файлы 👇» на
месте «Готовлю…» → текст с кнопками. Списание стоит до текста, а не после:
доставка — это файлы, текст лишь подпись под ними; упавший текст не должен
возвращать норму за доставленный доклад.

В MAX адаптер сам добавляет «☰ В меню» под каждое сообщение — под
результатом доклада кнопок стало две одинаковых. Адаптер теперь не
добавляет её, если в клавиатуре уже есть кнопка, ведущая в меню
(`app/adapters/max/keyboards.py`, `_leads_to_menu`).

## Шаг 2. Экран параметров

### Черновик в памяти, а не в базе (В6)

Раньше тема лежала в `users.pending` до выбора оформления и в
`users.retry_context` для «Повторить». Критерий В6 запрещает тему в базе,
поэтому всё, что видно на экране, — черновик `app/core/decks.py:Draft` в
памяти процесса (`MemoryHandoff[Draft]`, тот же механизм, что у связки
доклад ↔ презентация). Кнопки несут только жетон черновика (данные кнопки
Telegram — не больше 64 байт). В базе остаются только жетон в ожидании
(`await:pres:topic:<жетон>`, `await:pres:file:<жетон>`) и жетон в данных для
«Повторить».

- Живёт 6 часов; общий вес черновиков — не больше 200 МБ (`DRAFTS_MAX_BYTES`
  в `app/main.py`), при переполнении вытесняются самые старые.
- Миграция `e0a5b7c9d248` стирает из базы темы, оставшиеся от прежнего пути:
  ожидания `await:pres:theme:*`, `await:pres:from:*` и данные «Повторить»
  презентаций. Кто был посреди старого пути в момент выкладки, получит честный
  ответ «параметры устарели» и кнопку «Презентации».

### Что на экране и откуда значения

Только параметры `docs/API.md` §3.1, значения — из него же (константы в
`app/ports/presentations.py`), оформления — из `GET /v1/themes`. Значение из
данных кнопки приходит снаружи и проверяется по этим спискам; чужое не меняет
ничего. Таблица — в spec §4.10.

### Одна колода за нажатие (В4)

Слот сборки — в базе (`claim_presentation`), как и раньше. Черновик и жетон
доклада забираются только после доставки: упавшая сборка оставляет их, и
«Повторить» соберёт то же. Повторное «Собрать» после доставленной колоды
находит черновик взятым и отвечает «уже собрана».

### Старая кнопка (В5)

Нет черновика — «Эти параметры устарели…» с кнопкой «Презентации». Кнопки
выбора оформления из сообщений до выкладки отвечают так же.

## Шаг 3. По файлу

- **Проверки до провайдера.** Тип — по расширению имени до скачивания (API
  определяет тип так же, §3.1); размер — мессенджер сообщает до загрузки
  байтов, предел 20 МБ свой, а не общий предел раздела «Файлы»; содержимое —
  сигнатура PDF (`%PDF-`) или ZIP (`PK\x03\x04`) для docx и pptx, для txt —
  UTF-8 без нулевых байтов. Отказ оставляет ожидание файла: можно сразу
  прислать другой.
- **Тема из имени файла.** `Итоги_квартала.docx` → «Итоги квартала». Если из
  имени не выходит трёх знаков — тему спрашиваем: она станет заголовком
  титульного слайда, и «a» туда не годится.
- **Имя — из сообщения.** Telegram отдаёт файл под служебным именем
  `file_12.docx`; человеку на экране и провайдеру нужно его собственное.
- **Файл вытесняет доклад.** API принимает материал одним видом
  (`input.text` или `file`). «🗑 Без материала» убирает и то и другое; жетон
  доклада при этом не сжигается — кнопка под докладом остаётся живой.
- **В провайдер — multipart:** поле `params` с теми же параметрами в JSON и
  поле `file` (`app/adapters/presentations/fibonacci.py`).
- **В лог** при отказе — только `user_id` и признак «слишком большой».

## Решения, которые стоит проверить

1. **Строки «📦 Файлы: PPTX + PDF» на экране нет.** API всегда отдаёт оба
   файла, выбрать нечего; строка без кнопки обещала бы выбор. Вернуть её
   текстом — одна строка в `texts.deck_screen`.
2. **«📂 Тип: Доклад» показан, но без кнопки.** API принимает один тип
   (`doklad`, `pitch_deck` он отвергает).
3. **Подписи аудиторий — мой перевод:** 👥 Широкая, 🎓 Студенты, 🤝 Коллеги,
   👔 Руководство, 🛍 Клиенты, 💰 Инвесторы. Значения — из API, подписи — в
   `texts.AUDIENCE_LABELS`.
4. **«Проверь параметры», а не «Проверьте»** — обращение на «ты», как велено.
5. **Оформление по умолчанию — `graphite_light`**, как у самого API (раньше
   человек выбирал его сам). Нет его в списке — первое из списка.
6. **Черновики живут только в памяти.** Перезапуск сервиса или 6 часов —
   и экран отвечает «параметры устарели»; «Повторить» после перезапуска —
   тоже. Это цена В6: темы в базе нет.
7. **200 МБ на все черновики.** При файлах по 20 МБ это минимум десять
   одновременных черновиков с файлом; одиннадцатый вытеснит самый старый, и
   его владелец увидит «параметры устарели». Предел — одна константа в
   `app/main.py`; поднимать его стоит вместе с памятью сервиса на Railway.
8. **Файл, присланный, пока бот ждёт новую тему для экрана** («📝 Тема»), не
   становится материалом, а ведёт в меню раздела «Файлы», как любой файл без
   ожидания. Материал меняется кнопкой «📎 Материал».
