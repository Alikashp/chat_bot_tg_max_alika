## 1. MAX Bot API — что удалось установить точно

### 1.1 Базовые параметры

| Параметр | Значение | Откуда |
|---|---|---|
| Базовый URL | `https://platform-api2.max.ru` | `maxapi/connection/base.py:104` |
| Устаревший URL | `https://platform-api.max.ru` | `python-max-bot` (не мигрирован) |
| Авторизация | заголовок `Authorization: <token>` | `maxapi/bot.py:196` |
| Формат | JSON | — |
| Токен | у `@MasterBot` в мессенджере, команда `/create` | поиск |

Миграция на `platform-api2.max.ru` прошла в июле 2026; передача токена через
query-параметр больше не работает, только заголовок. Библиотека `python-max-bot`
(последний релиз май 2026) всё ещё по умолчанию ходит на старый домен — это прямой
признак, что она отстаёт от API.

### 1.2 Эндпоинты (полный список, `maxapi/enums/api_path.py`)

`/me`, `/commands`, `/chats`, `/messages`, `/updates`, `/videos`, `/answers`,
`/actions`, `/pin`, `/members`, `/admins`, `/uploads`, `/subscriptions`.

Нам из этого нужно ровно восемь операций:

| Операция | Метод и путь |
|---|---|
| Отправить сообщение | `POST /messages` |
| Изменить сообщение | `PATCH /messages?message_id=` |
| Получить URL загрузки | `POST /uploads?type=image` |
| Ответить на нажатие кнопки | `POST /answers?callback_id=` |
| Статус «печатает» | `POST /chats/{chat_id}/actions` |
| Подписать вебхук | `POST /subscriptions` |
| Проверить подписки | `GET /subscriptions` |
| Инфо о боте | `GET /me` |

### 1.3 Вебхук — критичные ограничения

Из докстринга `maxapi/methods/subscribe_webhook.py`:

1. **Порты.** Сервер обязан слушать один из: `80`, `8080`, `443`, `8443`,
   `16384`–`32383`. На Railway это не проблема: наружу торчит `443`, Railway сам
   терминирует TLS и проксирует на внутренний `$PORT`. Но при локальной отладке
   через туннель это надо учитывать.
2. **HTTPS обязателен с 25.05.2026.** Самоподписанные сертификаты не принимаются,
   нужен сертификат доверенного УЦ. Railway выдаёт валидный — годится.
3. **Секрет:** от 5 до 256 символов, только `A-Z a-z 0-9 -`. Передаётся при подписке,
   приходит в заголовке **`X-Max-Bot-Api-Secret`** каждого запроса. Это прямой аналог
   телеграмного `secret_token` (§3.5 промпта) — требование закрывается.
4. **Тайм-аут ответа — 30 секунд.** Одновременно активен либо вебхук, либо long
   polling, но не оба.

### 1.4 Формат обновлений — и почему это важно для идемпотентности

Ключевое отличие от Telegram, влияющее на архитектуру:

```python
# maxapi/webhook/aiohttp.py
event_json: dict[str, Any] = await request.json()  # ОДИН объект, не список
```

- **MAX присылает одно обновление на HTTP-запрос**, Telegram — тоже одно, но со
  сквозным `update_id`.
- В базовой модели обновления MAX (`types/updates/base_update.py`) есть **только**
  `update_type` и `timestamp`. **Сквозного `update_id` нет.**

Значит, дедупликация (§3.4.3 промпта) для MAX строится на составном ключе:

| Тип обновления | Ключ дедупликации |
|---|---|
| `message_created` | `message.body.mid` (`types/message.py:114`, уникальный id сообщения) |
| `message_callback` | `callback.callback_id` |
| `bot_started` | `("bot_started", chat_id, timestamp)` |

Это надо явно заложить в порт `Messenger`: у каждого входящего события есть
`dedup_key: str`, а как он вычисляется — дело адаптера.

Типы обновлений (`enums/update.py`): `message_created`, `message_callback`,
`message_edited`, `message_removed`, `bot_added`, `bot_removed`, `bot_started`,
`bot_stopped`, `chat_title_changed`, `user_added`, `user_removed`, `dialog_cleared`,
`dialog_muted`, `dialog_unmuted`, `dialog_removed`.

Нам нужны три: `message_created`, `message_callback`, `bot_started`. Подписываемся
только на них — меньше мусорного трафика.

### 1.5 Deeplink в MAX — работает

`types/updates/bot_started.py`:

```python
class BotStarted(BaseUpdate):
    chat_id: int
    user: User
    user_locale: str | None = None
    payload: str | None = None  # <-- вот это
```

Поле `payload` — прямой аналог телеграмного `/start ref_XXXX`. Значит реферальная
система (§2.7) и deeplink из бота презентаций (§2.1) реализуемы в MAX без
костылей. Это был главный риск для фазы 7 — он снят.

### 1.6 Клавиатуры в MAX — главное продуктовое расхождение с Telegram

Типы вложений (`enums/attachment.py`): `image`, `video`, `audio`, `file`, `sticker`,
`contact`, `inline_keyboard`, `location`, `share`.

Типы кнопок (`enums/button_type.py`): `callback`, `link`, `chat`, `message`,
`clipboard`, `open_app`, `request_contact`, `request_geo_location`.

**В MAX нет постоянной (reply) клавиатуры.** Есть только `inline_keyboard` —
вложение к конкретному сообщению.

Последствие для §2.1 и критерия приёмки №2 («клавиатура из 4 кнопок постоянна и не
пропадает ни на одном экране»):

- **Telegram:** `ReplyKeyboardMarkup(resize_keyboard=True, is_persistent=True)` —
  честная постоянная клавиатура, ровно как в промпте.
- **MAX:** та же четвёрка кнопок прикрепляется как `inline_keyboard` **к каждому
  исходящему сообщению**. Пользовательский результат тот же — четыре кнопки всегда
  под рукой, уйти с экрана всегда можно; механизм другой.

Это не отклонение от спеки, а ровно та разница, ради которой затевались порты и
адаптеры: `core/` возвращает абстрактное «показать главное меню», а как это
нарисовать — знает адаптер. **Проверка на стадии 9: если `core/` знает слова
`reply_keyboard` или `inline_keyboard` — это дефект.**

### 1.7 Отправка картинки — двухшаговая загрузка

Из `maxapi/utils/message.py` и `methods/get_upload_url.py`:

1. `POST /uploads?type=image` → возвращает временный `url` загрузки.
2. `PUT`/`POST` файла на этот `url` → ответ вида
   `{"photos": {"<key>": {"token": "..."}}}`.
3. Достать `token` первого фото и приложить к `POST /messages` как вложение
   `{"type": "image", "payload": {"token": "..."}}`.

Важная деталь: **вложение становится готовым не мгновенно.** Библиотека после
загрузки ждёт (`AFTER_MEDIA_INPUT_DELAY = 2.0`) и до 5 раз ретраит отправку
сообщения. То есть путь «фото → результат» в MAX по своей природе на пару секунд
длиннее, чем в Telegram. На UX это не влияет (у нас и так «Рисую… ~15 сек»), но
таймауты на отправку в MAX надо ставить с запасом.

`edit_message` в MAX есть (`maxapi/methods/edit_message.py`) — значит сценарий
§2.3 «сообщение "Рисую…" **заменяется** картинкой» реализуем в обоих мессенджерах
одинаково. Это второй снятый риск.

Статус «печатает» есть: `POST /chats/{id}/actions` с `typing_on`
(`enums/sender_action.py`), плюс `sending_photo`.

### 1.8 Ограничения, которые надо помнить

- Длина текста сообщения: **< 4000 символов** (`methods/send_message.py:71`).
  У Telegram — 4096. Берём общий безопасный предел **3900** в `core/`.
- С августа 2025 создавать и публиковать ботов в MAX могут **только верифицированные
  российские юрлица** — не ИП, не самозанятые, не физлица
  ([Хабр](https://habr.com/ru/articles/951326/)).

> **Это не техническая, а организационная блокировка, и о ней надо знать до фазы 7.**
> Код MAX-адаптера мы напишем и покроем тестами на моках, но без верифицированного
> юрлица бота нельзя будет опубликовать. Telegram-часть от этого не зависит.
> Если юрлица нет — фаза 7 всё равно имеет смысл (она доказывает, что архитектура
> честная), но выкатить MAX-бота в прод не получится. Нужно ваше решение по срокам.

## 2. Библиотека для MAX — сравнение и рекомендация

Проверены все три живых кандидата с PyPI: скачаны колёса, распакованы, прочитаны
исходники.

| | `maxapi` 1.2.2 | `aiomax` 2.12.5 | `python-max-bot` 0.4.1 |
|---|---|---|---|
| Последний релиз | 2026-08-15 (13 дней назад) | 2026-07-14 | 2026-05-05 |
| Релизов всего | 40 | 39 | 5 |
| Объём | 187 файлов, 17 542 строк | 10 файлов, 3 736 строк | 16 файлов, 1 629 строк |
| HTTP-клиент | aiohttp | aiohttp | **httpx** |
| Базовый URL | `platform-api2` ✅ | `platform-api2` ✅ | `platform-api` ❌ устаревший |
| **Вебхук** | ✅ есть, + проверка секрета | ❌ **нет вообще**, только polling | ✅ есть подписка |
| Типизация | pydantic + `py.typed` | нет | pydantic + `py.typed` |

| Лишние зависимости | backoff, magic_filter, aiofiles, puremagic | aiofiles | нет |

### Выбывшие

**`aiomax` — отпадает сразу.** В библиотеке нет ни одного упоминания вебхуков или
`/subscriptions`; она умеет только long polling. Требование §3.4.1 «webhook, не
polling» она не закрывает в принципе.

**`python-max-bot` — отпадает по риску отставания.** Технически он ближе всего к
нашему вкусу: тонкий клиент на httpx (совпадает со стеком), pydantic, без
навязанного диспетчера, всего 1 629 строк. Но: 5 релизов за всё время, последний —
за два месяца до июльской миграции API, и он до сих пор по умолчанию ходит на
мёртвый `platform-api.max.ru`. Для молодого и быстро меняющегося API это плохой
знак: библиотеку, похоже, не ведут.

### Рекомендация: `maxapi`, пинованный на 1.2.2, — но только как транспортный клиент

**Берём `maxapi`, используем из него класс `Bot` (транспорт) и НЕ используем его
`Dispatcher`, `Router`, фильтры и webhook-интеграции.**

Почему `maxapi`:

1. Это единственный кандидат, который одновременно поддерживает вебхуки, живёт
   (релиз 13 дней назад) и уже мигрирован на `platform-api2`.
2. MAX Bot API молодой и меняется рывками (смена домена в июле 2026, запрет HTTP в
   мае 2026). Живой мейнтейнер отслеживает эти изменения за нас — а официальную
   документацию мы, как выяснилось, читаем не всегда.
3. Полное покрытие нужных нам методов, pydantic-модели, `py.typed` — mypy будет
   работать.

Почему только транспорт, без фреймворка:

1. Второй диспетчер в проекте, где уже есть aiogram, — это дублирование роли и
   прямой путь к тому самому дублированию продуктовой логики, которое §8 промпта
   запрещает. Роутинг у нас один и живёт в `core/`.
2. Его webhook-интеграции тянут FastAPI или Litestar. У нас уже будет один
   HTTP-сервер (aiohttp, который и так приходит с aiogram) — второй веб-фреймворк
   в зависимостях не нужен.

Как приручаем (всё проверено в исходниках, параметры существуют):

```python
Bot(
    token=...,
    auto_requests=False,  # иначе на каждое событие библиотека делает
    # скрытые доп. запросы к API — лишняя латентность
    # и лишний расход лимитов
    default_connection=DefaultConnectionProperties(
        timeout=20,  # по умолчанию 150 с — недопустимо много
        sock_connect=5,
        max_retries=0,  # ретраи и circuit breaker — наши, из infra/;
        # два независимых слоя ретраев множат нагрузку
    ),
)
```

**Страховка от риска.** `maxapi` — пакет одного мейнтейнера с высокой частотой
релизов (40 за год), то есть ломающие изменения вероятны. Поэтому:
версия пинуется точно (`maxapi==1.2.2`), а вся работа с ней спрятана за наш
`Messenger`-порт. Нужные нам восемь эндпоинтов — это ~300 строк на httpx. Если
библиотека сломается или умрёт, мы пишем свой клиент за день и подменяем один
адаптер, не трогая `core/`. Это и есть смысл портов: **выбор библиотеки перестаёт
быть необратимым решением.**

## 3. Telegram

`aiogram 3.31.0` (релиз 2026-08-26, то есть библиотека активно живёт), Python
`>=3.10,<3.15`. Установлен и проверён вместе с `maxapi 1.2.2` и `pydantic 2.13.4` —
конфликтов нет.

Проверено практикой, что нужный нам режим работы поддерживается:

```
Dispatcher.feed_raw_update(self, bot: Bot, update: dict[str, Any], **kwargs) -> Any
Dispatcher.feed_update(self, bot: Bot, update: Update, **kwargs) -> Any
```

Это ключ к требованию §3.4.1 («хендлер вебхука отвечает 200 OK за < 50 мс»).
Штатный `SimpleRequestHandler` из aiogram обрабатывает апдейт **внутри** HTTP-запроса
— нам он не подходит. Мы пишем свой aiohttp-хендлер:

1. Проверить заголовок `X-Telegram-Bot-Api-Secret-Token`.
2. Прочитать JSON, взять `update_id`, проверить по дедупликатору.
3. Положить сырой `dict` в `asyncio.Queue`.
4. Вернуть `200 OK`.

А воркер уже вызывает `dp.feed_raw_update(bot, raw)`. Никакой работы с ИИ внутри
HTTP-запроса — требование выполняется буквально.

Постоянная клавиатура: `ReplyKeyboardMarkup(resize_keyboard=True, is_persistent=True)`.

## 4. Провайдеры ИИ

### 4.1 Рекомендация: один адаптер OpenAI-совместимого API на httpx

Не берём SDK `openai` (v3.5.0), берём `httpx` напрямую. Причины:

1. Промпт требует `httpx` и мок через `respx`. `respx` перехватывает **транспорт
   httpx**, поэтому запросы, идущие через наш собственный httpx-клиент, мокаются
   тривиально, а поведение SDK (свои ретраи, свой пул) пришлось бы обходить.
2. Нам нужен ровно один вызов — `POST /v1/chat/completions`. Это ~80 строк.
   Тянуть ради этого SDK со своей политикой ретраев, которая будет конфликтовать с
   нашей из `infra/retry.py`, — та же ошибка, что и с `maxapi`.
3. Формат `/v1/chat/completions` де-факто стандарт: на него отвечают OpenAI,
   OpenRouter и десяток других шлюзов. Один адаптер, смена провайдера — смена
   `base_url` и ключа в переменных окружения, без правок кода.

### 4.2 Текст: маппинг тариф → модель (§2.2)

Модель нигде не показывается пользователю и живёт в конфиге. Актуальные цены
(за 1 млн токенов вход/выход, [OpenAI API pricing](https://developers.openai.com/api/docs/pricing),
[BenchLM, август 2026](https://benchlm.ai/openai/api-pricing)):

| Класс | Модель по умолчанию | Цена вход/выход | Кому |
|---|---|---|---|
| эконом | `gpt-5-mini` | $0.25 / $2.00 | Free, Лайт |
| стандарт | `gpt-5` | $1.25 / $10.00 | Про, Макс |

Обе — переменные окружения (`LLM_MODEL_ECONOMY`, `LLM_MODEL_STANDARD`), не константы
в коде. `gpt-5-nano` ($0.05/$0.40) оставляем как запасной вариант, если счёт за
эконом-тариф окажется больно большим: качество ответа на «бесплатном ChatGPT» —
это и есть продукт, экономить на нём в первую очередь неправильно.

### 4.3 Картинки: тут главный риск проекта, и он финансовый

Нужны **два разных** сценария:

- §2.3 — текст → картинка;
- §2.4 — **фото пользователя + инструкция → изменённое фото** (лего-фигурка, сосед
  на фото). Это image-to-image редактирование, а не генерация с нуля.

Второе отсекает большинство дешёвых генераторов. `gpt-image-2` (OpenAI, апрель
2026) умеет и то, и другое одним контрактом и принимает до 16 референсных
изображений при редактировании ([GPT Image](https://en.wikipedia.org/wiki/GPT_Image)).
Поэтому **рекомендация — `gpt-image-2` через OpenAI Images API** как единственный
провайдер картинок на MVP: один контракт закрывает оба сценария.

**И вот цифра, которую нельзя пропустить.** Цена картинки 1024×1024
([costgoat](https://costgoat.com/pricing/openai-images), [OpenRouter](https://openrouter.ai/openai/gpt-image-2)):

| Качество | Цена за картинку |
|---|---|
| low | ~$0.006 |
| medium | ~$0.053 |
| high | ~$0.211 |

Считаем по спеке: бесплатный тариф даёт 3 картинки в день. 10 000 MAU — целевая
нагрузка из §1. Даже при консервативной оценке, что картинки реально рисует 20%
аудитории и в среднем по 2 штуки в день:

```
2 000 польз. × 2 карт./день × 30 дней = 120 000 картинок/мес
  при medium: 120 000 × $0.053 ≈ $6 360/мес   ← только за бесплатных пользователей
  при low:    120 000 × $0.006 ≈   $720/мес
```

Разница — на порядок, и это на бесплатной аудитории, которая по определению не
приносит выручки. Против выручки: 100 подписчиков Про по 599 ₽ — это ~$700/мес.

**Рекомендация: качество картинки — параметр тарифа в конфиге. Free → `low`,
платные → `medium`.** Это не фича в интерфейсе (пользователь про качество ничего не
знает и нигде его не выбирает — §1 запрещает «выбор модели пользователем»), а
константа в том же конфиге, где живёт маппинг тариф→модель для текста. Реализация —
одно поле в структуре тарифа.

Я не могу принять это решение за вас, потому что это решение про деньги, а не про
код: **подтвердите на стадии 3**, что free-тариф рисует в `low`. Если ответ «нет,
качество для всех одинаковое» — это тоже рабочий вариант, но тогда надо заранее
знать, что бесплатная аудитория будет стоить порядка $6 тыс./мес при выходе на
целевые 10 000 MAU, и закладывать это в юнит-экономику.

Альтернативы, которые я рассмотрел и отклонил для MVP:

- **OpenRouter Image API** (июнь 2026, 30+ моделей, единый эндпоинт, есть discovery
  возможностей — включая поддержку референсных изображений). Привлекателен как
  запасной аэродром и способ сравнить цены. Отклонён на MVP: лишний посредник в
  критическом пути, дополнительная задержка и ещё одна точка отказа при том, что
  наш адаптер и так позволяет переключиться сменой `base_url`.
- **Gemini image (nano banana)** — дешевле и быстрее, но другой формат запроса,
  то есть второй адаптер картинок. Для двух недель до прода — лишняя работа.
  Оставляем как понятный следующий шаг оптимизации после запуска.

## 5. Хранилище — рекомендация PostgreSQL, а не in-memory и не Redis

§3.3 промпта: «БД сейчас нет. Нужно создать и продумать логику». Структура из §4
предполагает `adapters/storage/memory.py` и `redis.py`.

**Рекомендация: PostgreSQL (управляемый, из Railway) + SQLAlchemy 2.x async +
asyncpg + Alembic. `InMemoryStorage` остаётся, но только для тестов.**

Обоснование от требований, а не от вкуса:

1. **Долговечность.** Railway при каждом деплое поднимает новый контейнер и гасит
   старый по SIGTERM. In-memory хранилище означает, что при выкатке обнуляются
   лимиты, рефералы и **оплаченные подписки**. Пользователь, заплативший 1 490 ₽,
   теряет тариф — это не «недостаток MVP», это возврат средств и репутационный
   ущерб. Приемлемо только на фазе 1, где ещё нет ни лимитов, ни денег.
2. **Атомарность.** Инвариант §2.2 («лимит не списывается за упавший запрос») и
   идемпотентность рефералки §2.7 — это транзакционные требования. В Postgres
   идемпотентность даётся даром: `UNIQUE (referrer_id, referee_id)`, вставка с
   `ON CONFLICT DO NOTHING`. Повторный `/start` по той же ссылке физически не может
   начислить награду дважды — это гарантия схемы, а не аккуратности кода.
   Self-referral — `CHECK (referrer_id <> referee_id)`.
3. **Почему не Redis.** Redis — прекрасный счётчик, но для данных о платежах его
   модель долговечности (снапшоты/AOF) слабее, а связей (пользователь → подписка →
   платежи → рефералы) он не умеет. Держать Postgres для денег и Redis для
   счётчиков — это два хранилища и две транзакционные границы там, где хватает
   одного. **Redis на MVP не берём вовсе.**
4. **Масштаб не пугает.** 10 000 MAU — это ~10 000 строк в `users`. Для Postgres
   это ничто; узкое место, как верно замечено в §3.4, — внешние API, а не БД.

Что это значит для §3.4.4 (rate limiting) и §3.4.3 (дедупликация): раз сервис на
MVP — **один процесс** (§5: «один сервис, один процесс»), token bucket и кэш
дедупликации живут в памяти процесса. Распределённые версии на Redis понадобятся
только при переходе на несколько реплик, и порт для этого уже будет.

Отклонение от структуры §4: вместо `adapters/storage/redis.py` будет
`adapters/storage/postgres.py`. Формально прошу подтвердить на стадии 3.

## 6. Оплата (фаза 8)

Оба канала подтверждены как реализуемые:

**Telegram Stars.** `sendInvoice` / `createInvoiceLink` с `currency="XTR"` и пустым
`provider_token`; в `prices` ровно один элемент; для подписки — параметр
`subscription_period` (в секундах), который требует именно `XTR`
([aiogram docs](https://docs.aiogram.dev/en/latest/api/methods/send_invoice.html)).
То есть месячная подписка §2.8 в Stars поддерживается нативно. Далее — обработчики
`pre_checkout_query` и `successful_payment`.

**ЮKassa.** `POST https://api.yookassa.ru/v3/payments` с обязательным заголовком
`Idempotence-Key`. Для автоплатежей: первый платёж с сохранением метода оплаты,
затем списания по `payment_method_id`
([ЮKassa](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/pay-with-saved)).
Подтверждение оплаты — вебхук от ЮKassa, то есть в приложении появится второй
входящий HTTP-эндпоинт.

Наценка 40% для Stars (§2.8) — коэффициент в конфиге, а не в коде.

**Python 3.12.** В контейнере есть 3.10–3.13; системный по умолчанию — 3.11,
поэтому работаем в venv на 3.12 и фиксируем версию в `runtime.txt`.

**Важное следствие про `respx`.** Он перехватывает транспорт httpx и, значит,
покрывает наши вызовы к ИИ-провайдерам — ровно как требует §3.1. Но `aiogram` и
`maxapi` работают на aiohttp, и `respx` их не увидит. Это не проблема, а
подтверждение архитектуры: адаптеры мессенджеров тестируются подменой **порта**
`Messenger` (обычный фейк), а не перехватом HTTP. Контрактные тесты из §4
(`tests/contract/`) проверяют, что и фейк, и реальный адаптер соблюдают один
протокол.

**Railway.** Healthcheck-путь настраивается в `railway.json`
([Railway Docs](https://docs.railway.com/deployments/healthchecks)). При выкатке
старому деплою шлётся `SIGTERM`, время на завершение регулируется переменной
`RAILWAY_DEPLOYMENT_DRAINING_SECONDS`
([Railway Docs](https://docs.railway.com/deployments/deployment-teardown)) — это и
есть окно для graceful shutdown из §3.4.7. Наш таймаут добивания очереди ставим
заведомо меньше этого окна.

**Нагрузочная проверка (критерий приёмки №12).** Отдельная библиотека не нужна:
30 rps в течение минуты — это 1 800 запросов, что закрывается скриптом на
`asyncio` + `httpx` в `scripts/loadtest.py`. Новых зависимостей — ноль.
