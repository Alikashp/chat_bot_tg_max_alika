# Грабли

На что этот проект уже наступал — в бою или на прогоне. Каждый пункт стоил
отладки, и каждый легко повторить заново, потому что код в этих местах выглядит
правильным.

## MAX: номер переписки и номер человека — разные числа

`POST /messages` в MAX принимает **либо** `chat_id`, **либо** `user_id`, и это
два разных номера. Номер переписки есть у разговора, который начал человек;
когда разговор начинаем мы сами (уведомление пригласившему, напоминание), у нас
на руках только номер человека. Подставить его в `chat_id` — значит отправить
сообщение в чужую переписку или никуда.

Поэтому у `Chat` есть признак `is_person`, и адресат раскладывается по полям в
`app/adapters/max/messenger.py`. Эта ошибка уже дважды уезжала в бой — сначала в
обычной отправке, потом в уведомлении пригласившему. Любой новый сценарий, где
бот пишет первым, проверять именно на этом.

## Провайдер картинок: одно фото и несколько — разные поля

Images API принимает исходники файлами: одно фото уходит полем `image`,
несколько — полем `image[]` (`app/adapters/ai/images.py`). Между нами и API
стоит шлюз, про разбор внутри которого мы ничего не знаем, поэтому части
multipart ещё и нумеруются: из MAX оба снимка приезжают под одним и тем же
`photo.jpg`, и одинаковые имена — единственное, чем шлюз мог бы склеить две
части в одну.

`input_fidelity` задаётся на каждый прикол отдельно
(`PRESET_INPUT_FIDELITIES`), а не одним общим значением: gpt-image-2 отвечает на
этот параметр `invalid_input_fidelity_model`, а модель у прикола своя
(`PRESET_MODELS`). Пустое значение выключает параметр целиком.

Правило на будущее: прикол с двумя фото идёт по другой ветке кода, чем все
остальные. Первый такой прикол — это выход на путь, который в бою ещё не
работал, сколько бы unit-тестов его ни покрывало: тесты проверяют нас, а не
шлюз.

## Где искать причину упавшей генерации

В Railway → Logs искать строку `preset_failed` с нужным `preset=`. В поле
`error` лежит `repr` ошибки целиком, а в нём — машинный код провайдера:

```
провайдер отклонил запрос: 400 (model_not_found)
```

Классы ошибок разделены по виновнику, и класс сам по себе уже ответ
(`app/adapters/ai/errors.py`):

- `ProviderRequestError` — 4xx. Виноват запрос: не та модель, не тот параметр,
  не тот формат. Повторять бессмысленно.
- `ContentRefusedError` — отказ по содержанию. Это **не** `ProviderRequestError`:
  если в логе он, дело не в модерации.
- `ProviderUnavailableError` — 5xx, 429, обрыв, таймаут. Повторяем, потом
  размыкаем предохранитель.
- `ProviderResponseError` — ответ пришёл, но картинки в нём нет.

В таблице `generations` хранится только имя класса — содержимое запросов и
ответов в базу не попадает намеренно. Машинный код провайдера есть только в
логе.

## Подписка на канал: бот должен быть админом канала

Проверка подписки — единственный вызов `getChatMember`, и работает он только
если бот администратор канала (`app/adapters/telegram/channel.py`). Без прав
Telegram отвечает `TelegramBadRequest`, и это «не смог проверить», а не «не
подписан»: бонус в таком случае не выдаётся и не отнимается, в лог уходит
`channel_check_refused`.

## ЮKassa

- **Магазинов два.** Ключи и идентификаторы у них разные, и оба кабинета надо
  настраивать отдельно.
- **Вебхук не принимается на веру:** он не подписан, поэтому статус платежа
  перечитывается у провайдера нашим ключом, и только потом выдаётся тариф.
- **Возврат не меняет статус платежа.** Платёж остаётся `succeeded`, возврат
  видно только по `refunded_amount`. Поэтому у нас отдельное значение статуса —
  иначе возврат нельзя отличить от неуспешной оплаты.
- **В уведомлении о возврате нет нашего `order_id`** — есть `payment_id`, по
  нему заказ и находится (`refunded_payment_id_of`).

## Очередь: сообщения одного человека обрабатываются параллельно

Воркеров по умолчанию 16 (`QUEUE_WORKERS`), и два обновления от одного человека
спокойно разъезжаются по разным воркерам. Порядок доставки не гарантирован.

Отсюда был баг «прислала сразу два фото»: второй обработчик читал устаревший
снимок сессии, а какое фото окажется первым, решала гонка. Лечится тремя вещами
сразу — ожидание на антифлуд-ограничителе, перечитывание пользователя внутри
защищённого участка и явный номер снимка (`CollectedPhoto.order`). Любой
сценарий, который собирает несколько сообщений в одно действие, проверять на
это.

## Реестр пресетов

Порядок записей в `config/presets.py` — это сразу три порядка: кнопки в меню,
картинки в альбоме-примере и смысл «сначала без замка, потом с замком».
Переставили запись — переставились и картинки.

На каждый прикол нужен `assets/presets/<id>.jpg`. Без файла прикол есть в меню,
а примера у него нет; смоук-прогон это ловит отдельной проверкой.

## Тесты

- **Без `TEST_DATABASE_URL` контрактные тесты по базе пропускаются молча.**
  Прогон зелёный, а половины гарантий нет. В CI база поднимается сервисом.
- **Фейк должен отдавать управление.** Фейковый мессенджер без единого `await
  asyncio.sleep(0)` внутри загрузки фото делал тест на гонку зелёным и без
  исправления самой гонки. Если тест проверяет одновременность, фейк обязан
  быть честной корутиной.
- **Правки через веб-интерфейс GitHub не проходят линтер.** Длинные строки в
  промптах пресетов один раз уехали в `main` и уронили CI 74 ошибками E501.
  После ручных правок в вебе — сразу `ruff format --check .`.
- **Смоук запускать `python -u` в файл** и прочитать файл один раз в конце.
  Опрашивать лог в цикле — это только сожжённые токены. И если смоук замолчал —
  смотреть не на бота, а на драйвер: упавший драйвер выглядит как зависший бот.

## Тесты и окружение — фаза 10

- **`metadata.create_all` не добавляет колонки в уже существующие таблицы.**
  Тесты по базе создают схему именно так, и после правки `schema.py` старая
  локальная база падает на новой колонке, хотя код верен. Перед прогоном:
  `psql ... -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"`. В CI база
  каждый раз новая, там этого не видно.
- **PostgreSQL в облачном контейнере.** Его нет после перезапуска контейнера,
  а запущенный без `-c unix_socket_directories=/tmp` он падает на правах к
  `/var/run/postgresql`. Рабочая команда — `pg_ctl ... -o '-p 55432 -c
  listen_addresses=127.0.0.1 -c unix_socket_directories=/tmp'`.
- **respx считает вызов только после ответа.** Тест, который ждёт
  «запрос ушёл» по `respx.calls`, пока ответ задержан, висит вечно. Сигнал
  надо ставить внутри обработчика (`asyncio.Event`).
- **Управляемые часы не отдают управление.** Фейковый `sleep`, который только
  двигает время, не пускает другие корутины: вторая сборка начиналась уже
  после конца первой, и тест предела одновременных сборок был бы зелёным и
  без предела. Одновременность проверяется задержкой на настоящем событии.
- **Мутация может превратить падающий тест в висящий.** Снятый предел пускал
  вторую сборку на тот же задержанный опрос. Ожидание в таком тесте — под
  `asyncio.wait_for`. А висящий прогон мутаций нельзя гасить целиком: файл
  восстанавливается в `finally` скрипта, и убить надо только дочерний
  `pytest`.
- **`pkill -f` по шаблону убивает и собственную команду,** если шаблон есть
  в строке запуска, — вместе со всем, что шло в ней следом.

## Постоянное меню Telegram меняется только сообщением, которое его несёт

Новые подписи в коде сами до человека не доезжают: reply-клавиатура
обновляется, только когда приходит сообщение с ней. А клавиатура у сообщения
одна — ответ с inline-кнопками меню не принесёт. До фазы 10 из-за этого новое
меню видели только нажавшие `/start`. Теперь у человека хранится версия меню
(`users.menu_version`), и после первого ответа меню обновляется — один раз
на версию (`router._refresh_menu`, `TelegramMessenger.refresh_menu`).
Меняете меню — ничего делать не нужно: версия считается из подписей сама.
